**Consistent hashing (согласованное хеширование)** – это алгоритм распределения данных по узлам (серверам), при котором изменение количества серверов приводит к перераспределению лишь *минимального количества ключей*.

При классическом распределении данных (например, в горизонтальном масштабировании баз данных или кэшей) используется формула: 
`Server Index = hash(key) % N`
где \(N\) — это текущее количество серверов.

**Главная проблема:** как только \(N\) меняется (добавили новый сервер для увеличения мощности или один из старых серверов упал), *знаменатель формулы меняется для всех*.
- Почти все существующие ключи (до 99%) мгновенно меняют свой целевой сервер.
- В масштабах реальной системы это вызывает **«кэш-шторм»** (cache storm): кэш на серверах становится бесполезным, все запросы одновременно идут в основную базу данных, из-за чего вся система может лечь. Начинается массовая миграция гигабайтов данных по сети.

**Согласованное хеширование** решает эту проблему с помощью концепции **хеш-кольца (Hash Ring)**:
1. **Кольцо пространства:** Представьте числовую прямую от \(0\) до \(2^{32}-1\) (диапазон значений обычной хеш-функции вроде MD5 или SHA-1), соединенную в круг.
2. **Размещение серверов:** Идентификаторы серверов (например, их IP-адреса) хешируются. Полученные значения определяют координаты серверов на этом кольце.
3. **Размещение данных:** Ключ данных (например, ID пользователя) хешируется той же функцией и тоже получает свою координату на кольце.
4. **Поиск сервера:** Чтобы понять, куда сохранить или откуда считать данные, система находит координату ключа на кольце и движется **по часовой стрелке** до тех пор, пока не встретит первый сервер. Этот сервер и отвечает за ключ.

Почему это решает проблему?
- **При добавлении сервера:** Новый узел встает в определенную точку кольца. Он забирает себе часть ключей только у своего соседа _против_ часовой стрелки. Остальные серверы и их ключи вообще не затрагиваются.
- **При удалении сервера:** Его ключи просто переходят к следующему за ним серверу по часовой стрелке. Опять же, вся остальная сеть работает без изменений.

**Виртуальные узлы (Virtual Nodes)**
Если серверов мало (например, три), они могут распределиться по кольцу неравномерно. Один сервер будет отвечать за 70% кольца, а остальные два – за оставшиеся 30%. Возникнет *дисбаланс нагрузки (hotspots)*.

Чтобы этого избежать, используют **виртуальные узлы**: каждый реальный сервер хешируется сотни раз с разными префиксами (например, `ServerA#1`, `ServerA#2`, `ServerB#1`...). Его копии равномерно перемешиваются по всему кольцу. Если один сервер выйдет из строя, его нагрузка плавно распределится по всем остальным узлам, а не упадет на одного соседа.

**Consistent hashing** критически важно для высоконагруженных распределенных систем:
- **Распределенные NoSQL базы данных:** В Apache Cassandra и Amazon DynamoDB алгоритм используется для определения того, на каких именно узлах кластера должны храниться конкретные строки и их реплики.
- **Распределенный кэш:** Сети Memcached или кластеры Redis используют этот подход, чтобы при плановом расширении пула кэш-серверов пользователи не разлогинивались, а система не теряла данные из оперативной памяти.
- **Балансировка нагрузки (Load Balancing):** Прокси-серверы вроде NGINX или HAProxy используют этот алгоритм (режим `hash ... consistent`), чтобы закреплять sticky sessions запросы конкретного пользователя за одним и тем же бэкенд-сервером, даже если общее число бэкендов меняется.
- **Сети доставки контента (CDN):** Для эффективного кэширования тяжелых медиафайлов на серверах, близких к пользователю.
